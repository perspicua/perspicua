Perspicua Build Order
=====================

This file is the ORDER in which to build things so every layer rests on a solid
one below it. The full catalog of ideas lives in IDEAS.txt; this file is about
sequencing and dependencies, not describing every feature.

Guiding rule: correctness of the foundation before breadth of features. A bug in
the scheduler, the MMU, or the buffer cache costs 10x more once demand paging,
threads, and a network stack sit on top of it.

================================================================================
PHASE 1: FOUNDATION HARDENING  (finish filling the holes)
Goal: Complete the half-built features so the base is dependable.
================================================================================

   1. Libc essentials: ctype.h, strerror, strdup/strndup, setjmp/longjmp.
      Every porting attempt hits these immediately; all are small.
   2. Remaining POSIX syscalls: getppid, dup, pread/pwrite, gettimeofday +
      clock_gettime, nanosleep, fstat, truncate/ftruncate. One or two functions each.
   3. SIGSTOP / SIGCONT (STOPPED state + wake on CONT) — the kernel half of job control.
   4. /proc/mounts, /proc/cpuinfo, /proc/stat — trivial procfs files tools expect.
   5. Shell: $? , $VAR expansion, correct pipeline exit codes.
   6. `just test` target + test_vfs / test_fat32 / test_signals / test_pipe.
      The riskiest subsystems (FS, signals, IPC) currently have no tests.
   7. Core POSIX utility *binaries*: ps, kill, mkdir, rm, cp, mv, touch, wc, grep.
      (The syscalls exist; the programs don't — you can't create a file from the
      shell except via > redirection.)


================================================================================
PHASE 2: ROBUSTNESS PRIMITIVES  (the load-bearing infrastructure)
Goal: Build the reusable mechanisms that every advanced feature depends on, so we
build them ONCE and correctly rather than re-inventing ad-hoc versions.
================================================================================
   1. Generic wait-queue / condition-variable primitive.
      Replaces the hand-rolled queues in tty/pipe/sd. Prerequisite for select/poll,
      futexes, and any new blocking driver.
   2. Sleeping-lock family on top of it: rwsem, semaphore, completion (kmutex exists).
   3. preempt_count (preemption safety) so ordinary spinlocks are safe across a tick.
   4. Graceful OOM: replace PANIC-on-allocation-failure with unwinding error returns.
   5. Unified buffer cache: collapse the duplicate page cache + block cache into one.
   6. VFS inode/dentry cache with refcounted vnodes (stop allocating a vnode per
      lookup; gives stable inode identity).
   7. Panic backtrace via the existing symbol table + a dmesg ring buffer.

  Rationale: Phases 3+ (poll, demand paging, threads) all assume these exist. Doing
  them now avoids retrofitting correctness into ten call sites later.


================================================================================
PHASE 3: DEVELOPER EXPERIENCE & BASIC I/O
Goal: Make Perspicua a place you can actually work and observe.
================================================================================
   1. I/O multiplexing: select / poll (needs the wait-queue primitive).
   2. Core /dev nodes: /dev/null, /dev/zero, /dev/tty, /dev/random, /dev/urandom.
   3. RTC / wall-clock driver so timestamps survive reboots.
   4. Shell quality of life: globbing, history, tab completion; then scripting
      (if/for/while, &&/||).
   5. A ramdisk block backend + tmpfs — fast scratch space and better test fixtures.


================================================================================
PHASE 4: ADVANCED MEMORY & STORAGE  (the heavy lifting)
Goal: The core mechanisms that define a modern OS. Each depends on Phase 2.
================================================================================
   1. munmap / mprotect / a real VMA list (mmap can't be undone today).
   2. brk/sbrk or anonymous-VMA heap so libc malloc grows properly.
   3. Demand paging: fault-in ELF and file pages from the unified buffer cache
      instead of loading eagerly. Big win for startup time and RAM.
   4. Shared-memory IPC (MAP_SHARED / shm) — needed for a graphics server.
   5. A second, inode-based filesystem (ext2 or a small journaling FS): validates
      the VFS abstraction and provides the crash consistency FAT32 lacks.


================================================================================
PHASE 5: CONCURRENCY & SECURITY
Goal: Use the hardware fully and safely.
================================================================================
   1. Threads: clone() + TLS (tpidr_el0) + per-thread signal state. Revisit the
      one-task-per-process assumptions (schedule()'s lock-free process read,
      main_task-targeted signal delivery) at this point.
   2. Futexes -> a real pthreads library.
   3. Full preemptive, priority/MLFQ scheduling with cross-core load balancing.
   4. Security: W^X audit, ASLR + user stack canaries, PAN/SMAP-equivalent, then a
      uid/gid + capability model.


================================================================================
PHASE 6: STRATEGIC EXTENSIONS  (long-term)
Goal: Broaden into networking, graphics, and beyond.
================================================================================
   1. Network stack (a NIC driver via USB/PCIe, then LWIP or a minimal UDP/IP).
      Depends on I/O multiplexing (Phase 3) and a real device stack.
   2. Graphics server (Wayland-lite). Depends on shared-memory IPC (Phase 4) + input.
   3. Dynamic linking (ld.so + shared objects) — mostly a user-space loader problem;
      do it once there are many large binaries.
   4. Virtualization via EL2 — running guest OSes on top of Perspicua.


================================================================================
When in doubt: correctness of the foundation beats breadth of features. Finish and
test a layer before building the next one on top of it.
================================================================================
