Perspicua Testing
=================

How the test suites are built and run, what a passing run looks like, and the
rule about hardware validation before a release.

--------------------------------------------------------------------------------
THE MODEL
--------------------------------------------------------------------------------
There is no separate test binary and no host-side unit framework — the system
tests itself on the target (QEMU, or real hardware), printing assertions to the
serial console, and the harness reads that console output to decide pass or
fail. Tests run in two phases.

KERNEL PHASE. Compiled INTO the kernel, gated behind CONFIG_TESTS, run at boot:
before init starts, except the post-init suites, which run just after it is
created. These live in kernel/tests/ (test_pmm, test_slab,
test_mmu, test_sched, test_vfs, test_fat32, test_pipe, test_mutex,
test_signals, test_uaccess, and others). test.c wires them together; test.h
declares the entry points.

USERSPACE PHASE. Ordinary programs in user/apps/, typed at the shell prompt by
the harness once the kernel phase finishes. Some behavior is only reachable
from here: a signal handler runs on the way back to EL0, which a boot-phase
kernel test task never does, so SA_RESTART, sigaltstack and catchable faults
(user/apps/test_restart.c) cannot be tested any other way. test_tools runs the
command-line tools (head, sort, find, du, ...) on known input through pipes
and checks their output byte for byte. test_libc covers the C library, down to
when stdout holds output back and when it lets go. test_syscall and test_fcntl
check syscall semantics and refusals, test_stop_cont job-control signals,
test_sh the shell through sh -c, and stress -s 1 runs the stress tests with a
fixed seed.

--------------------------------------------------------------------------------
SEPARATE BUILD TREE
--------------------------------------------------------------------------------
Test builds go into build-test/, kept apart from the normal build/ tree. This
is deliberate: toggling CONFIG_TESTS changes compiler defines, and sharing one
tree would force a full reconfigure and rebuild every time you switched between
a normal run and a test run. Two trees means each stays warm.

--------------------------------------------------------------------------------
RUNNING THE TESTS
--------------------------------------------------------------------------------
  just test              Build the test kernel (CONFIG_TESTS=ON) into
                         build-test/, build the SD image, and run headless in
                         QEMU via scripts/run_tests.sh. Exits non-zero unless
                         every check in WHAT A RUN LOOKS LIKE holds. This is the
                         command CI and the pre-merge gate use.

  just build-tests       Build the test kernel without running it.

  just test-shell        Build the test kernel and run it interactively in QEMU,
                         dropping to the shell after the suites finish — for
                         poking at the system in the same configuration the
                         tests ran under.

Override configuration the same way as a normal build, e.g.:
  just cmake_args="-DCONFIG_SMP=OFF -DCONFIG_LOCKDEP=OFF" test
An override lasts for that one command; the next `just test` without it builds
the defaults again. `just config build-test` shows what the tree last built.

--------------------------------------------------------------------------------
WHAT A RUN LOOKS LIKE
--------------------------------------------------------------------------------
scripts/run_tests.sh boots the kernel headless and watches the serial log for
completion markers rather than waiting for a fixed time. The run is a PASS only
when ALL of the following are true:

  - No suite printed "[FAILED]".
  - The kernel did not print "KERNEL PANIC".
  - It did not time out (180 s for the whole run by default; just's
    test_timeout raises it, as CI does for its slower runners).
  - Every kernel completion marker was reached:
      "reached target: kernel self-test complete"
      "reached target: scheduler test complete"
      "reached target: post-init test complete"
  - Every kernel suite in KERNEL_SUITES printed "test: <name>: N tests [OK]",
    with N at least the minimum listed beside it.
  - Every userspace suite in USER_SUITES printed "<name>: all N tests passed"
    with N at least its minimum, and exited with status 0.
  - The kernel printed none of FAIL_MARKERS, the errors that do not panic.
  - Job control and line editing at the live prompt held: Ctrl-Z at an idle
    prompt and a background `sh &` leave the shell reading, `fg` on a stopped
    pipeline waits for every stage, and a terminal size report, the Delete key
    and a lone Esc leave no stray bytes on the command line.
  - Every line of the console burst, typed without waiting for each echo, came
    back intact. On a failure the harness prints /proc/tty's drop and error
    counts.

The minimums catch a suite that stops running some of its tests: a dropped
call or an early return still prints [OK], just with a smaller N.

Checking completion separately from failure matters: a suite that never ran
prints nothing at all, so "no failures" is not the same as "everything ran." A
run that hangs or panics before a marker is a failure, not a pass.

Some kernel suites need a live user process to target, so they run after
/bin/init.elf has been created — that is the "post-init" marker. The harness
then waits for the shell prompt and feeds each userspace suite in over QEMU's
stdin.

--------------------------------------------------------------------------------
THE HARDWARE-VALIDATION GATE
--------------------------------------------------------------------------------
QEMU is the everyday loop, but it is not the whole story: timing, the SD card,
and interrupt behavior differ on real silicon. Per branch_workflow.txt, the dev
branch must be tested ON HARDWARE before it is promoted to main. `just test`
passing in QEMU is necessary, not sufficient — main is meant to be something you
could flash to a board right now. hardware.txt covers the board setup.

--------------------------------------------------------------------------------
ADDING A SUITE
--------------------------------------------------------------------------------
In the kernel:
  1. Add kernel/tests/test_<thing>.c, using TEST_SUITE_BEGIN, TEST_ASSERT* and
     TEST_SUITE_END from test.h: they print [FAILED] per failed assertion and
     "test: <name>: N tests [OK]" for a clean suite. The tests/*.c glob in
     kernel/CMakeLists.txt picks the file up.
  2. Register it so it runs from the appropriate phase (self-test, scheduler, or
     post-init) in test.c / test.h.
  3. Run `just test`, then add "<name>:<N>" to KERNEL_SUITES in
     scripts/run_tests.sh with the N its [OK] line printed.

In userspace:
  1. Add user/apps/test_<thing>.c. It is picked up by the glob in
     user/CMakeLists.txt and lands in /bin automatically.
  2. Count with CHECK() from user/apps/utest.h and end main with
     `return utest_summary("<name>");`, which prints the line the harness
     reads and returns non-zero on failure.
  3. Add "<name>:<N>" to USER_SUITES in scripts/run_tests.sh, or it will build
     and never be run.
  4. Break one assertion on purpose and confirm `just test` exits non-zero. A
     gate that cannot fail is not a gate.
